# Owned Clock and Random native drivers

Prepared 2026-10-03 before implementation, following [the Clock/Random decisions](clock-random-modules.md). Reviewed current Rust helper scopes, synchronous scalar signatures, AsyncContext cancellation/logging/finalizer state and compiler reachability. The other instance retains core-plan ownership.

Primary sources fetched online: pinned [Clock](https://unpkg.com/effect@4.0.0-rc.118/src/Clock.ts), [Random](https://unpkg.com/effect@4.0.0-rc.118/src/Random.ts), [internal Random](https://unpkg.com/effect@4.0.0-rc.118/src/internal/random.ts), and Rust std [SystemTime](https://doc.rust-lang.org/std/time/struct.SystemTime.html). Official reads/draws are synchronous effects; draws are finite doubles in `[0,1)` and Boolean mapping is strictly greater than 0.5. SystemTime epoch conversion can fail for pre-epoch timestamps and needs an explicit signed path. This record admits milliseconds only; it does not claim wall/monotonic nanos or seeded parity.

## Decisions before implementation

- **DRV-001 — concrete owned context only when needed.** Default live wall milliseconds call a direct std helper, retaining zero context for synchronous functions. Injected Clock and scripted Random require an explicit invocation-owned context. Existing asynchronous functions reuse AsyncContext; newly contextual synchronous functions use a generated SyncContext. Pure functions and unrelated synchronous functions retain their signatures. Alternative: universal context arguments or thread-local service state; both add unnecessary costs or hidden identity/lifecycle. Revisit at shared host-service ownership or cross-task service inheritance.
- **DRV-002 — implementation selection precedes driver injection.** Planning selects live Clock versus injected Clock and requires explicit scripted Random admission. Native test hosts configure the chosen context through typed setters, never RPC payload fields. An injected Clock can carry live/stable/scripted modes; Random has no implicit live or seeded fallback. Empty Random scripts fail as internal defects when drawn, bypassing typed recovery. Alternative: silently use a host random crate or reset a seeded generator each call; neither has the admitted semantics. Revisit with a separately researched live Random backend or ISAAC identity model.
- **DRV-003 — fixed reachable fields, separate payloads.** Each generated context kind retains only Clock/Random state reachable by its functions. Clock mode stores live, stable f64 or an owned Vec plus cursor; Random stores an owned Vec plus cursor. No universal Arc/trait object/heap record accompanies Numbers or Bools. Script Vec allocation occurs during host setup; empty context construction and stable clocks require no script allocation. Module-wide AsyncContext sharing can enlarge unrelated async futures within that artifact; record that limit and measure layouts. Revisit per-function context specialization when measured growth warrants it.
- **DRV-004 — checked signed epoch and scripts.** Live milliseconds use signed integer magnitude around UNIX_EPOCH, checked within JavaScript safe integer bounds before conversion to f64. Pre-epoch submillisecond samples need floor semantics: `floor(signed elapsed seconds * 1000)`, rather than negating truncated magnitude. Invalid/exhausted scripts panic with explicit internal-defect messages; mutable cursors advance once per completed read/draw. No suspension or cancellation check occurs inside the atomic driver read itself; existing helper boundaries govern interruption. Revisit nonfinite clock injections only with explicit Number semantics and reference evidence.
- **DRV-005 — observer clocks remain an explicit boundary.** Existing native log timestamps/spans use their established std clock implementation. Injected computation Clock readings do not silently replace logger timing. Reference differential scripted-read fixtures must suppress observer clock reads or use a stable provider; a generic full Clock service substitution claim needs an observer integration gate. Timer scheduling retains the existing real-time bounded Sleep adapter, not virtual time. Revisit at observability timing injection or coordinated virtual timers.

## Proposed integration contract

The core agent owns implementation selection/types, checked nodes and references. Lowering consumes the agreed selection and independently derives per-function service context reachability from checked semantic nodes. `ClockReadMillis` and `RandomDraw` remain Number/Never computations; Random Boolean stays existing comparison after exactly one draw.

Native SyncContext exposes a `new()` constructor and selected `set_clock_stable(value)`, `set_clock_script(values)` and `set_random_script(values)` methods. AsyncContext exposes the same selected methods while preserving `new(cancellation)` and existing cancellation/finalizer APIs. Scripts are supplied by native test/host code after construction. Default injected Clock starts live; default Random script is empty and cannot accidentally produce values. No new crate is required.

Generated helper call threading includes context for computations in a contextual function, while pure expression helpers retain existing parameter lists. Synchronous service functions continue to return Result directly; services must not classify them as asynchronous or introduce Tokio. Existing frame policies and error channels remain unchanged. CLI/native RPC integration must deliberately construct or refuse required contexts; it must not pick test scripts from untrusted user arguments.

## Evidence required before delivery

Compare live clock type/range and injected stable/scripted reads against official services. Test exact `0`, `0.5`, just above 0.5 and below 1 Random draws, conditional skipped reads, repeat/retry, recovery and finalizers without cursor rewind. Verify missing backend selection refuses before lowering, and invalid/exhausted scripts bypass domain catch. Run native direct-context probes for sync and async functions, two-context isolation/interleaving, both frame policies, and cancellation around real Sleep.

Measure empty/stable context construction, script setup allocation, unpolled contextual future construction and layout separately. No-service artifacts must retain signatures/dependencies/context state; live-Clock-only synchronous artifacts must remain std with no service context allocation. TypeScript compiler/authoring objects are separate from generated runtime state. Claims about live SystemTime allocation, enabled future layout or script memory remain unmeasured until probes run.

## Implementation review

The native scaffold now emits direct live reads, reachability-selected owned contexts, validated script setters and concrete cursor state. Compiler/core integration preserves synchronous classification and passes normalized implementation selection into lowering. Missing Random selection refuses in planning and has a defensive lowering check. No runtime dependency was added.

The first native compile exposed a backend syntax error: synchronous Clock/Random helpers emitted a bare `Ok(...)` expression instead of a function body block. The backend now wraps both through typed `Rs.block` and `Rs.ok`, following the existing RefGet pattern. Type checking alone could not detect this generated Rust error; native execution validation remains required before delivery. Scripted-driver invalid/exhausted faults remain explicitly outside full Effect defect/finalizer parity.

Focused Clock/Random validation passed **7/7** in **52.94s** after that fix, including fresh native debug/release probes under both failure-frame policies. The probes exercise sync/async contexts, scripted ordering/branch skips, repeat/retry/recovery, two-context interleaving, cancellation with cleanup, live defaults and invalid/exhausted host configuration. Script buffers and watch channels are prepared before allocation counting: context construction, moving validated buffers and constructing an unpolled service future add zero allocations; the specified synchronous scripted workload also adds zero allocations. This does not measure script-buffer allocation, logging, polling timers or general fault handling. No-service context/future layouts and enabled layouts are measured by the fixture; retain its concrete outputs rather than extrapolating a universal per-service byte cost. Full parent validation and host RPC conformance are separate gates.

The final strengthened focused run passed **7/7** in **53.86s**. On the fixture's Rust 1.98.1/x86-64 build, both debug and release report enabled SyncContext **64 bytes**; enabled AsyncContext/interleaved future are **160/464 bytes** with frames disabled and **168/504 bytes** with bounded frames. The no-service release baseline AsyncContext/sleep future is **96/312 bytes** disabled and **104/320 bytes** bounded. Logging is reachable in both artifacts. The service fields add 64 context bytes in these artifacts; the future programs differ, so their full size delta cannot be attributed solely to services. Captured outputs are retained by the conformance fixture's optional measurement sink. These figures describe these concrete artifacts, not ABI or general layout guarantees.
