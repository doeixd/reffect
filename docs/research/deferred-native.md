# Lexical Deferred native preparation

Recorded 2026-10-03 before implementation, after the fallible task kernel. This is the native adapter proposal accompanying the stable Deferred module design; implementations and measured costs must be distinguished from this preparation.

Reviewed AGENTS, PLAN/PROGRESS, [coordination admission](coordination-modules.md), [structured tasks](structured-concurrency.md), [fallible native](fallible-native.md), existing lexical Ref binder elaboration, capture filtering, async context and the fixed-arity coordinator. Checked [published Effect 4.0.0 Deferred](https://unpkg.com/effect@4.0.0/src/Deferred.ts), [Rust Waker](https://doc.rust-lang.org/std/task/struct.Waker.html) and [Mutex](https://doc.rust-lang.org/std/sync/struct.Mutex.html) online on this date. Installed stable source agrees: await registers a removable callback; completion retains its effect/outcome, detaches all resumes before broadcasting, and repeated completion returns false. Typed succeed/fail installs an immutable Exit; arbitrary complete/completeWith is a distinct deferred gate.

## Native decisions

- **DN-001 — Lexical inline owner.** Store a `DeferredState<A,E>` in its owning computation, borrowed as `&DeferredState` by child helpers. Bool/U64/Unit payloads and Bool/U64/Unit/Never errors are Copy. Keep `Option<Result<A,E>>` inside an inline std Mutex, with no Arc or boxed cell. Read-only handle borrowing shares one state; copying the state would violate first-completion identity. Handles cannot appear in outputs, composite values, long-lived services or independent invocations. Parent groups await children before the lexical owner can close.
- **DN-002 — Statically specialized slot bound.** The proposed topology has at most three ordinary children, plus one permitted infallible two-child Race inside one infallible All child. Its maximum live leaf computations is four. Sequential continuation/finalization does not overlap an additional parent computation while children are still executing. Specialize each owner as `DeferredState<A,E,N>` using the checked maximum live leaf count of its body (`N` from one through four). Preserve that capacity on the build-owned helper parameter, rather than adding it to scalar payloads or a runtime handle object. This is a compiler topology bound, not a user-visible restricted Deferred queue capacity. Other nesting, task creation during cleanup, detached tasks and fallible nested groups remain refused. Topology widening must revisit this proof before admission.
- **DN-003 — Registration and completion linearize under one lock.** An await future checks retained completion and registers its own slot in one critical section. Completion installs the retained Result and takes the whole Waker array under the same lock. Wake the detached cohort after releasing the lock. This prevents lost wakeups, reentrant unregister from skipping a waiter and lock recursion. Never hold a MutexGuard across await or user work.
- **DN-004 — Cancellation owns one slot.** Each await future records its optional slot, updates its Waker on repoll and removes only that slot in Drop. Interruption uses the existing independent child watch channel and biased select; dropping that await future unregisters it without clearing completion or changing another slot. Completion is final, so detached slots cannot be reused by a newly registered pending waiter. Late awaiters read the retained Copy Result immediately.
- **DN-005 — No scalar metadata.** Failure trails are created at the individual await occurrence using the existing selected frame policy. Retained completion contains only A/E, without frames or annotation snapshots. Payloads never gain provenance/coordination wrappers. The audited coordination scaffold is emitted only when a Deferred owner/operation is reached; no new crate/features are required beyond the already admitted Tokio async kernel.
- **DN-006 — Conservative fault boundary.** Poisoned locks and exhausted checked slots indicate trusted-host/compiler invariant faults, not representable typed errors. Refuse unsupported topology before emission; do not silently overwrite a waiter or allocate an unbounded spill buffer. General Cause completion, fiber IDs, arbitrary completion effects and non-Copy payloads remain separate gates.
- **DN-007 — Synchronous resume is an unresolved admission gate.** Stable `doneUnsafe` invokes the detached resume callbacks synchronously in registration order. Resumed waiter continuations run until their next genuine suspension before the next callback and before the completing producer continues. Merely waking Tokio futures, acknowledging inside an await future's `poll`, or yielding the producer once does not preserve this contract. In particular, a waiter can complete another Deferred: an adapter's own pending acknowledgement phase must not be mistaken for a genuine Effect suspension, or the outer completion will resume its next waiter too early. No authoring/native support is claimed until a safe bounded continuation-turn adapter or an explicit, defensible admission restriction passes these controlled traces. Isolated state tests cannot discharge this scheduler gate.

## Alternatives and acceptance

Tokio oneshot is consuming delivery and cannot support multiple/late awaiters. Watch retains a broadcast value but adds a heap allocation per owner and imposes its own sender/receiver lifecycle. Notify plus a retained result can work but requires enable-before-check and still needs cancellation-safe waiter handling. A bounded inline future adapter is smaller for this compiler-known borrowed topology. A RefCell owner is not Sync and cannot safely support Send native host futures; std Mutex keeps the owner shareable without Arc allocation.

Acceptance must compare two waiting children plus a producer and late awaiter; first/losing completion Booleans; typed failure; a race-canceled waiter while another remains; completion before first polling; parent interruption; and LIFO cleanup before owner close. A direct poll/Waker probe should cover registration-versus-completion, Waker replacement and Drop reclamation without depending on sleeps. Measure owner/future/context bytes and retained/allocation counts across construction, registration, completion and cancellation under None/Bounded frames. Existing fallible/infallible group gates remain valid; this design adds no new fallible nesting or Cause capacity.

## Next design questions

The next implementation decision must answer these together, before enabling the authoring surface:

1. **What is a continuation turn?** A resumed waiter may log, map values, recover a typed failure or complete another Deferred before it actually suspends. Define the native poll boundary that acknowledges this entire turn. Distinguish genuine pending await/timer/group work from internal pending completion machinery. A wake notification or a result copied out of the mutex is not that boundary.
2. **How does registration order reach nested children?** Slot reuse means physical slot index is not registration order. A detached fixed cohort needs an explicit order representation. A task coordinator must be able to poll the selected waiter, including a leaf of the permitted inner Race, before later cohort members and the producer. Biased input-order polling alone does not prove registration-order execution.
3. **How do reentrant completion and cancellation interact?** Nested completion must finish its synchronous resume cohort before the outer waiter continues. Cancellation of the producer must not abandon installed completion or silently skip the rest of the detached cohort. Cancellation of a waiter must reclaim only its registration and still await its admitted cleanup. Include a waiter whose cleanup completes a signal consumed by another producer; this is relevant to the isolation witness, not an optional exotic API.
4. **Where does scheduler state live?** Prefer a reached-only, borrowed, inline turn owner associated with the enclosing task region. A fixed turn/cohort stack and stable checked child identities are candidates, not accepted implementations. Prove lifetimes through nested groups and awaited cleanup without raw pointers, a process-global registry, `Arc` per Deferred or metadata on payloads. If the safe Rust representation requires separate lifetime-bearing helper parameters, keep them distinct from ordinary `AsyncContext` and retain const-capacity specialization in lowering.
5. **What bound closes the proof?** Four live leaf waiters bounds one completion cohort; it does not by itself bound reentrant completion-stack depth, especially if a resumed continuation enters a sequentially nested task region or completes several owners. Derive a separate checked bound, or refuse the unproved path explicitly. Repeated executions must reuse identity/cohort storage without monotonic counters that can overflow.

No Rust layout or allocation measurements are available yet. The eventual cost report must separate retained payload/Mutex/waiter state, ordered completion cohort storage, continuation-turn bookkeeping, cloned executor Wakers and existing task watch channels. Measure construction, parked await, losing/winning completion, nested completion, independent cancellation and repeated slot reuse; report peak as well as retained allocations. Confirm that a program without reachable Deferred keeps its previous generated source, context layout and allocation budget. Also report helper signature/code growth and whether specialization increases generated binary size or Cargo compile time materially.

Status: preparation only. The fallible kernel has landed and repository synchronization is verified; the continuation-turn design remains a gate before native feature edits. State linearization/cancellation and scheduler equivalence are separate acceptance obligations.
