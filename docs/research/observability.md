# Observability research and design preparation

Research started 2026-09-30 and finalized 2026-10-01 for the user-requested telemetry, OpenTelemetry, logging, stack-trace and metadata design. This is research for future implementation; no observability crates or public authoring APIs are installed by this change.

## Prior work and constraints

Reviewed PLAN.md, PROGRESS.md, AGENTS.md, the revised compiler/milestone/conformance documents, compiler API and runtime lowering references, and the current kernel/compiler/reference/native runner. Milestones 0/1 and the initial synchronous milestone 2 profile are implemented. Source provenance is currently an IR path, not a TypeScript source map. Named compiler/reference `Effect.fn` wrappers can supply official Effect stack annotations; the native scalar bridge returns values/errors without matching annotations. RPC, native Logger/Tracer/Metric adapters, async Scope and fibers are not implemented.

Preserve symbolic IR, official Effect reference interpretation, explainable capability/dependency planning and optional Rust dependencies. Observability must start with source metadata and synchronous events, then acquire request propagation and exporter lifecycle with RPC; it must not require the full concurrency milestone first. Keep original discussion documents intact and add explicit later-update links.

## Alternatives and decision

Use compiler-owned source/provenance tables plus a small semantic observability context/record model. Generate instrumentation into ordinary Rust `tracing`, OTel SDK instruments/records, and exporters. Keep those crates behind selected profiles. Reuse Effect Logger/Tracer/Metric and its OTLP modules on the JS/reference/compiler side.

Rejected: a second generic telemetry runtime/OTLP implementation; tracing every Expr/helper; using Rust Debug or native backtraces as source semantics; treating all tracing events as both logs and span events; encoding semantic metrics as specially named log messages; attaching mutable debug fields to operation identity; gating logical failure stacks on span sampling. Those approaches lose semantic precision, create duplicate export, or add avoidable overhead.

Prefer direct SDK log records for compiled Effect logs where a tracing bridge cannot preserve Fatal severity, typed fields or context. Keep the appender bridge available for ordinary Rust dependency logs. Use tracing-opentelemetry for spans and explicit SDK metrics, with a verified adapter/context bridge between them. Avoid a second metrics registry until a workload justifies it. Explicitly distinguish Effect compatibility export from OTel service-boundary conventions.

## Acceptance and remaining decisions

The design must specify provenance capture without a source transformer, preservation through DAG sharing/optimization, separate logical/native/distributed traces, failure payload/annotation compatibility, context isolation through await/fork/join/finalizers, logging field/severity/stream behavior, signal-independent filters, deterministic in-memory conformance, bounded queues/shutdown, source-map/build artifacts and explainable dependency selection.

Settle exact API names, IDs/source-map schema, thresholds/buffer defaults and release feature compatibility during the first implementation slice. First implement source metadata and synchronous logging/logical frames; then request spans/propagation and OTLP lifecycle at milestone 3. Full Cause observation, FiberRef joins, interruption stacks and finalizer/task tracing wait for their existing milestones. Measure disabled and enabled overhead rather than promising zero cost for all profiles.
