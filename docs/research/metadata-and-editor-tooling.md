# Metadata cost, Rust emission and Volar research

Checked 2026-10-01 against reffect `a0fa91f`, before the performance probe and design/plan updates. This is design evidence; proposed profiles and editor adapters are not implemented.

## Current implementation and questions

Reviewed PLAN, PROGRESS, source maps, observability, migration tooling, runtime lowering, immutable builders, provenance collection, source artifacts and Rust emission. TypeScript Expr/Fn/Computation/EffectFn wrappers have a source reference; unannotated wrappers share one frozen empty object. An annotation creates a wrapper and metadata snapshot, retaining the semantic node/binder/body. Source sites reference shared file snapshots. The current annotation path validates/snapshots twice. Lowering retains provenance and generated ranges; the Boolean/u64 builder emitter always hashes/serializes source and build artifacts, including when users supply no annotations. There is no implemented metadata-off compile profile.

Rust values remain plain bool/u64/Result; provenance is external JSON. No source field, metadata hash lookup, Arc, Box or runtime instrumentation is generated by these annotations. Existing generated CLI argument strings/Vec allocations and inline(never) helper boundaries predate source metadata. Compiler cost and future runtime observability cost must be assessed separately.

The source collector retains full IR paths internally, compact edges on the wire, strong build-local indexes, and source text in compilation memory. Hashing/serialization creates temporary buffers. It avoids expanding shared DAG paths but does not establish a universal linear bound on full-path storage for deep graphs. Limits are safeguards, not performance evidence.

## Primary evidence

- [Volar upstream README](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/README.md) describes language-core, language-service/server, kit and editor adapters. Reviewed upstream commit `44d58aee30d1d476c8ad3f6f5581b288d7185d1e` (2026-03-05). [Language interfaces](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-core/lib/types.ts) expose snapshot-based virtual code, incremental/disposal hooks, mappings and per-region verification/completion/semantic/navigation/structure/format flags. Disabling reporting does not necessarily skip typechecking.
- [Volar mapping implementation](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/source-map/lib/sourceMap.ts) uses offset/length arrays and lazy lookup indexes, not ECMA-426 serialization. [Offset translation](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/source-map/lib/translateOffset.ts) accepts endpoints inclusively and translates unequal lengths by clamping relative offsets; this cannot stand in for reffect's half-open whole-origin resolution. [Language-core caches](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/language-core/index.ts) use WeakMaps keyed by snapshots/virtual code inside a language instance, illustrating an editor-cache lifetime strategy.
- npm registry observations: [language-core](https://registry.npmjs.org/@volar/language-core/latest) and [source-map](https://registry.npmjs.org/@volar/source-map/latest) both `2.4.28`, registry gitHead `882cd56d46a13d272f34e451f495d3d62251969a`. Inspected main declares `2.4.28` but is a different commit. No package is installed or integration compatibility inferred from version equality. The package licenses are MIT.
- [Volar TypeScript adapter](https://github.com/volarjs/volar.js/blob/44d58aee30d1d476c8ad3f6f5581b288d7185d1e/packages/typescript/lib/quickstart/createLanguageServicePlugin.ts) depends on the JavaScript TypeScript language-service/plugin API. This is not proof of compatibility with our observed TypeScript `7.0.2` native checker or Effect-tsgo. A standalone compiler-diagnostic LSP consumer does not require this plugin API. The checked kit README refers to createLinter/createProject, while current kit source exposes createChecker/createFormatter; use pinned source/types when implementing, not copy its example blindly.
- [Rust type layout](https://doc.rust-lang.org/reference/type-layout.html) specifies primitive sizes, padding and transparent wrappers; [PhantomData](https://doc.rust-lang.org/std/marker/struct.PhantomData.html) is zero-sized. A transparent domain newtype can retain representation, but an actual extra SiteId field needs storage; type-level tags cannot encode a changing execution occurrence for free.
- [Rust statics](https://doc.rust-lang.org/reference/items/static-items.html) have program-lifetime storage, distinct from heap allocation. A static array of compact site records and string literals needs no per-record heap allocation; a static HashMap initialized at runtime still allocates. [Arc](https://doc.rust-lang.org/std/sync/struct.Arc.html) allocates shared data on the heap and uses atomic reference counts. [Weak](https://doc.rust-lang.org/std/sync/struct.Weak.html) refers to reference-counted allocations; it is not a GC WeakMap for moving/copyable primitives.
- [JavaScript WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap) avoids retaining keys, but entries/metadata still need memory and lookup; keys cannot be numbers/bigints, and keys cannot be enumerated. A wrapper-keyed side table can hold optional authoring metadata; a semantic-node-only table loses distinct use occurrences. Scoping/lifetime matter more than calling a map static.
- [tracing callsites](https://docs.rs/tracing-core/latest/tracing_core/callsite/index.html) separate static metadata and cached interest from dynamic event values. Registration/subscribers can still allocate. [Rust formatting arguments](https://doc.rust-lang.org/std/fmt/struct.Arguments.html) borrow arguments; deferred synchronous formatting does not imply safe retention of those borrows in an asynchronous exporter queue.

## Decisions and proportional validation

Keep semantic values unwrapped; distinguish compiler provenance, static runtime site descriptors, dynamic execution annotations and owned exported records. Prefer build-local interned tables and optional object-keyed TypeScript associations, immutable snapshots and compact IDs at emission. Do not adopt a global runtime metadata map, per-number tags or per-node reference-counted metadata. Retain direct references until a measured side-table change justifies its complexity; profile artifact creation and retained graphs too.

Specify independent authoring capture, artifact retention and runtime instrumentation policies. Next runtime frames/logging slice must include disabled-path allocation/latency/code-size verification and explicit frame bounds. Source maps alone can remain external with no native instrumentation. Stripping diagnostics must not change domain outcomes or silently erase observable log/span semantics.

Volar is a useful optional editor/virtual-document candidate, not a runtime or semantic compiler dependency. Start with compiler diagnostics and generated preview; use Volar when a real virtual-code/navigation consumer warrants it. Prefer native editor-language services for existing TS; forbid generated-Rust inverse edits without compiler rules.

Keep Rust helpers typed by syntactic role and target types, emitting through one source writer. Introduce validated identifiers, types, expressions/blocks/items and origin scopes only as real lowering needs them. TypeScript typing cannot prove Rust ownership or validity; rustc plus native/reference conformance remain required.

Validation will compare annotated/unannotated builder and full compile costs in isolated processes, retained JS heap after GC, artifact bytes and generated-source identity. This measures current explicit annotations, not a nonexistent stripped compiler or future logging. Record workload, runtime/toolchain, repetitions and limitations; no native throughput overhead percentage follows from a compiler probe.

## Recorded probe — 2026-10-01

Added [a reproducible compiler probe](../../scripts/measure-source-metadata.mjs). Node 24.19.0/linux-x64, five isolated samples per variant, alternating order, 128 functions × 16 additions, 16 shared explicit sites and 128 named function boundaries. Each child warms a tiny compile and measures construction/full Compile.run plus post-GC retained heap; it does not measure transient peak allocation, native execution or a nonexistent metadata-off compiler.

Observed medians: unannotated/annotated construction 8.7/10.8 ms; compilation 442/436 ms; retained program 636,880/773,200 bytes; program plus artifact 6,124,264/6,518,616 bytes; auxiliary JSON 2,462,421/2,569,876 bytes. Both emit 115,086 identical generated Cargo/Rust bytes, with 4,352 origins/occurrences. Compilation timing differences are inconclusive in this small noisy sample. Baseline map materialization/retention is a more substantial opportunity than the source-reference slot. Workload shape and site sharing limit generalization. The [design](../metadata-cost.md) records the policy/storage choices and follow-up acceptance.

A review repeat after replacing probe offset constants with equivalent length-derived offsets again produced identical generated sources and the same artifact byte counts. Timings varied (builder medians 9.1/13.2 ms; compile 483/474 ms), while retained program heap stayed approximately 631/773 kB. This reinforces the timing/heap caveats rather than a universal overhead claim. Installed TypeScript 7.0.2 tsc is a Node launcher for a native executable, confirming that JS language-service plugin compatibility needs independent verification.
